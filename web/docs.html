사용 기술과 역할

각 컴포넌트의 도입 목적과 상세 역할

Docker Compose

여러 서비스를 하나의 개발/운영 스택으로 묶기 위해 사용합니다. 이 프로젝트는 Web, API, PostgreSQL, Qdrant를 각각 독립된 컨테이너로 실행합니다. 회사/팀 프로젝트에서는 로컬 환경 차이를 줄이고 배포 구조를 명확히 하기 위해 Docker 기반 구성이 중요합니다.

FastAPI

AI 백엔드 API 서버입니다. 문서 등록, 청크 생성, 벡터 인덱싱, 검색, RAG 답변, Agent 실행, 로그 조회를 API로 제공합니다. Python 기반 AI 라이브러리와 연결하기 쉽고, 빠르게 MVP를 만들기 좋아 선택했습니다.

PostgreSQL

원문과 이력을 저장하는 관계형 데이터베이스입니다. documents, document_chunks, ask_logs, feedback_logs, content_sources, crawled_pages 같은 데이터를 저장합니다. Vector DB가 검색 인덱스라면, PostgreSQL은 정합성과 추적 가능성을 담당합니다.

Qdrant

의미 기반 검색을 위한 Vector DB입니다. 문서 청크를 embedding vector로 변환해 저장하고, 사용자 질문과 의미적으로 가까운 문서 조각을 찾아냅니다. PostgreSQL이 일반적인 조건 검색에 강하다면, Qdrant는 문장 의미 유사도 검색에 특화되어 있습니다.

LangGraph

Agent Workflow를 그래프 형태로 구성하기 위해 사용합니다. 질문을 먼저 분류하고, RAG 답변, 시스템 상태 안내, 사용법 안내, 범위 외 질문 처리 등으로 분기합니다. 이는 실제 AI 서비스에서 모든 질문을 무조건 LLM/RAG로 보내지 않기 위한 구조입니다.

Nginx

Web UI와 API를 하나의 진입점으로 제공하기 위해 사용합니다. 브라우저는 8771 포트로 접속하고, Nginx는 정적 웹 페이지와 /api 요청을 각각 적절한 내부 서비스로 전달합니다.

LLM Provider (Google / OpenClaw)

LLM 호출부를 추상화했습니다. Google API를 이용한 번역/요약이나, 개인 데스크탑에서 실행 중인 OpenClaw (Gemma/Qwen 등)를 로컬 모델로 연동할 수 있습니다.

RAG 파이프라인 흐름

문서 수집부터 의미 검색, 답변 생성까지의 단계별 처리
1. 문서 등록 ↓ 2. Chunk 생성 ↓ 3. Embedding 생성 ↓ 4. Qdrant Vector Index 저장 ↓ 5. 사용자 질문 Embedding ↓ 6. Semantic Search ↓ 7. 검색 결과를 Context로 구성 ↓ 8. LLM 답변 생성 ↓ 9. Sources와 함께 응답 반환 ↓ 10. Logs / Feedback 저장

RAG는 LLM이 사전학습된 지식만으로 답변하지 않고, 등록된 문서와 레퍼런스를 검색해 그 내용을 근거로 답변하도록 만드는 구조입니다.

이 프로젝트는 RAG 과정을 하나의 숨겨진 함수로 처리하지 않고, 문서 등록, 청킹, 인덱싱, 검색, 답변, 로그를 각각 분리해 눈으로 확인할 수 있게 만들었습니다. 이렇게 분리하면 답변이 부정확할 때 원인이 검색 문제인지, 청킹 문제인지, 프롬프트 문제인지, LLM 문제인지 분석할 수 있습니다.

PostgreSQL과 Qdrant는 왜 둘 다 필요한가

데이터 영속성 관리와 의미 검색의 역할 분리

PostgreSQL과 Qdrant는 서로 대체 관계가 아니라 역할이 다릅니다.

PostgreSQL은 원문 문서, 청크, 질문 로그, 답변 로그, 피드백, 크롤링 기록처럼 정확히 보존하고 추적해야 하는 데이터를 저장합니다. Qdrant는 문서 청크의 embedding vector를 저장하고, 질문과 의미적으로 가까운 문서 조각을 빠르게 찾는 검색 인덱스 역할을 합니다.

즉, PostgreSQL은 원본과 이력을 관리하고, Qdrant는 의미 검색을 담당합니다. 실무 AI 백엔드에서는 이처럼 영속 저장소와 Vector Search 저장소를 분리하는 구조가 자주 사용됩니다.

  • documents: 원문 문서
  • document_chunks: 검색 단위로 나눈 문서 조각
  • ask_logs: 질문/답변 실행 기록
  • ask_source_logs: 답변에 사용된 source 기록
  • feedback_logs: 사용자의 평가
  • content_sources: 수집 대상 사이트/소스
  • crawled_pages: URL 수집 결과

LangGraph Agent Workflow

질문 의도를 선행적으로 분류
classify_intent ├─ rag_query → RAG 답변 ├─ system_status → 시스템 상태 설명 ├─ how_to_use → 사용법 안내 ├─ out_of_scope → 범위 외 질문 안내 └─ needs_clarification → 추가 질문 요청

기본 RAG Ask는 모든 질문을 검색 기반 답변으로 처리합니다. 하지만 실제 AI 서비스에서는 모든 질문을 같은 방식으로 처리하면 안 됩니다.

예를 들어 사용법을 묻는 질문, 시스템 상태를 묻는 질문, 투자 추천처럼 범위를 벗어난 질문, 너무 짧고 모호한 질문은 각각 다른 방식으로 처리해야 합니다.

이 프로젝트는 LangGraph를 사용해 질문 의도를 먼저 분류하고, 적절한 노드로 라우팅합니다. LangGraph를 사용하면 Agent의 처리 흐름을 node와 edge로 명확하게 표현할 수 있습니다. 이는 복잡한 AI 기능을 단순한 if/else 코드가 아니라, 관찰 가능하고 확장 가능한 workflow로 설계하기 위한 실험입니다.

테스트 콘솔 페이지는 단순 테스트 페이지가 아니라, AI 백엔드의 전체 처리 흐름을 단계별로 확인하기 위한 학습용 콘솔입니다. 아래 순서대로 실행하면 RAG/Agent 시스템이 어떻게 동작하는지 이해할 수 있습니다.

  1. Health 확인: API와 시스템이 살아 있는지 확인합니다.

  2. Ask 실행: 검색 결과를 context로 사용해 LLM 답변을 생성합니다.
  3. Agent Ask 실행: LangGraph가 질문 의도를 분류하고 적절한 경로로 처리하는지 확인합니다.
  4. Logs / Feedback 확인: 질문, 답변, source, latency, feedback을 확인해 개선 포인트를 찾습니다.

Qdrant vs PostgreSQL (pgvector) 아키텍처 결정
왜 pgvector가 아니라 Qdrant인가?

PostgreSQL도 pgvector 확장을 사용하면 embedding vector 저장과 유사도 검색이 가능합니다.
하지만 이 프로젝트에서는 RAG 아키텍처를 명확히 이해하고 설명하기 위해 관계형 영속 저장소와 벡터 검색 저장소의 역할을 의도적으로 분리했습니다.

PostgreSQL은 원문 문서, 청크, 질문 로그, 피드백, 수집 소스처럼 정합성과 이력 관리가 중요한 데이터를 저장합니다.
Qdrant는 embedding vector와 검색용 payload를 저장하고, 사용자 질문과 의미적으로 가까운 chunk를 찾는 semantic retrieval layer 역할을 합니다.

작은 규모에서는 pgvector도 충분히 좋은 선택입니다.
다만 이 프로젝트에서는 전용 Vector DB의 구조, payload filtering, Docker 기반 배포, 향후 확장 가능성을 학습하고 보여주기 위해 Qdrant를 선택했습니다.

용어 설명
  • embedding vector는 텍스트, 이미지, 코드 같은 비정형 데이터를 숫자 배열로 바꾼 것이다.
  • payload는 vector와 함께 저장하는 부가 정보, 즉 메타데이터다.
    • pgvector/PostgreSQL: 가능. 컬럼 또는 jsonb로 표현
    • Qdrant: 가능. vector point의 기본 구조로 자연스럽게 제공
  • semantic retrieval layer는 사용자의 질문과 의미적으로 가까운 문서 조각을 찾아주는 검색 계층이다.
  • payload filtering은 vector search를 할 때 메타데이터 조건을 함께 거는 것이다.

PostgreSQL은 relational filtering이 강하다.
복잡한 join, transaction, business rule, SQL 분석은 PostgreSQL이 훨씬 좋다.

PostgreSQL + pgvector VS Qdrant
구분 PostgreSQL + pgvector Qdrant
정체성 PostgreSQL에 vector 타입과 유사도 검색을 추가하는 확장 처음부터 vector search를 위해 만든 전용 Vector DB
주 역할 관계형 데이터 + 벡터 검색을 한 DB 안에서 처리 embedding vector 저장, 유사도 검색, payload filtering에 특화
데이터 저장 방식 일반 테이블 컬럼에 vector 타입 저장 collection 안에 point 저장. point = vector + payload
원문/업무 데이터 관리 매우 강함. SQL, transaction, join, constraint, audit에 유리 가능은 하지만 RDB처럼 복잡한 업무 정합성 관리에는 부적합
벡터 검색 가능. exact search, HNSW/IVFFlat 같은 ANN index 사용 가능 핵심 기능. HNSW 기반 vector search, payload filter, collection 관리에 특화
메타데이터 필터링 SQL WHERE 조건으로 가능 payload filter로 가능. Vector search와 같이 쓰기 좋게 설계
RAG MVP 단순성 DB를 하나만 쓰므로 구조가 단순 DB가 하나 더 생기므로 구조는 조금 복잡
RAG 아키텍처 학습성 “PostgreSQL 하나로 통합 구현”을 보여주기 좋음 “RDB와 Vector DB 역할 분리”를 보여주기 좋음

문서 등록 단계

RAG 파이프라인의 ingestion 단계

문서 등록은 RAG 파이프라인의 ingestion 단계입니다.

사용자가 직접 입력한 문서나 URL에서 수집한 reference를 공통 Document 모델로 정규화하고, PostgreSQL의 documents 테이블에 원문으로 저장합니다.

원문을 저장하는 이유는 chunking, embedding, indexing은 모두 파생 데이터이기 때문입니다.

원문이 있어야 chunk 전략이나 embedding 모델이 바뀌었을 때 재처리할 수 있고, 답변이 잘못되었을 때 어떤 source에서 온 문서인지 추적할 수 있습니다.

source와 license는 RAG 답변의 근거 추적성과 사용 가능 범위를 관리하기 위한 메타데이터입니다.

이 정보는 RAG 답변의 근거 추적성과 안전한 재사용을 위해 필요합니다. 특히 URL 기반 reference는 외부 문서이기 때문에 source URL과 license 정책을 함께 저장해, 나중에 답변 근거 표시나 원문 노출 범위를 관리할 수 있게 했습니다.

Manual document와 URL reference는 입력 경로는 다르지만, 최종적으로 documents 테이블에 저장되는 공통 구조로 통합했습니다.

그래서 이후 chunking, vector indexing, semantic search, RAG ask, agent ask는 동일한 파이프라인을 재사용할 수 있습니다.

4. 방식별 설명
4-1. Character Chunking

현재 방식이다.

문서 전체를 800자 단위로 자르고, 다음 chunk는 이전 chunk의 마지막 100자를 다시 포함한다.

현재 코드가 정확히 이 방식이다. chunk_text()는 start = 0에서 시작해 end = start + chunk_size까지 자르고, 다음 start를 chunk_size - chunk_overlap만큼 이동시킨다.

예: chunk_size = 800 overlap = 100 step = 700 Chunk 0: 0 ~ 800 Chunk 1: 700 ~ 1500 Chunk 2: 1400 ~ 2200

장점

구현이 쉽다. 빠르다. 디버깅이 쉽다. MVP에서 전체 pipeline 검증에 좋다.

단점

문장 중간에서 잘릴 수 있다. 문단 중간에서 잘릴 수 있다. Markdown heading 구조를 모른다. 코드 블록을 중간에서 자를 수 있다. 표를 망가뜨릴 수 있다.

평가

dev-ai의 첫 구현으로는 맞다. 하지만 계속 이 방식만 쓰면 RAG 품질이 금방 한계에 부딪힌다.

4-2. Recursive / Paragraph-aware Chunking

이 방식은 character chunking보다 한 단계 좋다.
핵심은 “무조건 800자로 자르지 말고, 자연스러운 경계를 먼저 찾자”다.

예상 우선순위: 1. 큰 섹션 2. 문단 3. 문장 4. 줄바꿈 5. 공백 6. 그래도 안 되면 character 기준 절단

이 방식은 LangChain의 RecursiveCharacterTextSplitter 계열 아이디어와 비슷하다. 프로젝트 문서에서도 향후 RecursiveCharacterTextSplitter처럼 의미 단위, 문단, 문장 등을 우선하는 전략을 도입할 수 있다고 정리되어 있다.

장점

현재보다 문맥이 덜 깨진다. 구현 난이도가 아주 높지는 않다. 문단형 문서에 효과가 좋다. 기존 DB 구조를 거의 그대로 쓸 수 있다.

단점

문서 구조가 지저분하면 완벽하지 않다. Markdown heading, 코드 블록 등은 별도 처리가 필요하다.

dev-ai 추천

가장 먼저 할 개선이다.
기존 CharacterChunker를 바로 없애기보다 chunk_strategy = character | recursive 형태로 병행하면 좋다.

4-3. Token-aware Chunking

Token-aware 방식은 글자 수가 아니라 LLM tokenizer 기준으로 자른다.

800 characters가 아니라 500 tokens 같은 식이다.

왜 중요하냐면 LLM 비용과 context window는 보통 token 기준이기 때문이다.

장점

LLM context window 관리에 좋다. prompt 길이 예측이 쉬워진다. embedding model 입력 제한을 넘길 위험이 줄어든다.

단점

tokenizer 의존성이 생긴다. OpenAI, Anthropic, local model마다 tokenizer 차이가 있을 수 있다. 문단 의미 경계를 보장하지는 않는다.

dev-ai 적용 방향

document_chunks에 token_count, chunk_strategy 필드를 추가하면 좋다.
Qdrant payload에도 넣으면 좋다. {"chunk_strategy": "token", "token_count": 482}

평가

RAG 답변 품질 자체보다 운영 안정성에 좋다. 즉 “LLM 입력 길이 관리” 측면에서 중요하다.

4-4. Heading-aware Chunking

Heading-aware는 Markdown, HTML, docs 구조를 활용한다.

예: # BomTS Dev AI ## Architecture ### FastAPI ### PostgreSQL ### Qdrant ## RAG Pipeline ### Ingestion ### Chunking

이 구조를 기준으로 chunk를 만든다.

장점

기술 문서에 매우 강하다. README/docs/공식문서에 적합하다. 검색 결과가 설명 가능해진다. UI에서 section 표시가 가능하다.

검색 결과를 이렇게 보여줄 수 있다.
Document: RAG Pipeline Guide
Section: Chunking > Overlap
Score: 0.82

단점

heading이 없는 문서에는 효과가 약하다. Markdown/HTML/PDF parser가 필요하다. 문서 구조가 잘못되어 있으면 품질도 흔들린다.

dev-ai 적용 방향

PostgreSQL document_chunks에 heading_path, section_title, chunk_strategy 필드가 있으면 좋다.

Qdrant payload에는: { "heading_path": "RAG Pipeline > Chunking", "section_title": "Chunking", "source_type": "docs" }

평가

dev-ai는 README, docs, AI Reference 문서가 많기 때문에 매우 잘 맞는다.

4-5. Metadata-rich Chunking

이건 chunk를 어떻게 자르느냐보다, chunk에 어떤 정보를 같이 붙이느냐의 문제다.

예: { "document_id": 3, "chunk_index": 7, "title": "LangGraph Agent Workflow", "source": "manual", "license": "private", "source_type": "learning_note", "category": "agent", "heading_path": "Agent > LangGraph > Workflow", "published_at": null, "chunk_strategy": "heading_recursive", "token_count": 438 }

장점

검색 결과 설명이 좋아진다. Qdrant payload filtering에 유리하다. source/category/license 기준 검색이 가능하다. Evaluation log 분석이 쉬워진다. Reference Pipeline과 잘 맞는다.

단점

metadata 설계가 필요하다. 필드가 많아지면 관리가 복잡해진다. 잘못된 metadata는 검색 품질을 오히려 해칠 수 있다.

적재 성능/디스크 영향

metadata는 vector 자체에 비하면 작다. 하지만 chunk 수가 많아지면 payload도 같이 늘어난다.

디스크 증가: content 중복 > vector 저장량 > metadata

보통은 metadata 추가보다 overlap으로 인한 content 중복이 더 큰 문제다.

dev-ai 추천

강력 추천. 특히 현재 AI Engineering Reference Pipeline을 키우려면 metadata-rich 구조가 필요하다.

4-6. NLTK 기반 Chunking

NLTK는 전통적인 NLP toolkit이다. 문장 분리, tokenization, corpus 기반 처리 등에 많이 쓰인다. NLTK 자체는 오래된 대표적인 NLP 교육/연구용 toolkit으로, 다양한 NLP 모듈과 corpus를 제공한다. (arXiv)

NLTK 기반 chunking은 보통 이렇게 한다. 1. 문서를 문장 단위로 분리 2. 문장들을 chunk_size 안에 들어오도록 묶음 3. 필요하면 overlap 문장 몇 개 추가

장점

문장 중간 절단이 줄어든다. character 방식보다 자연스럽다. 구현이 비교적 간단하다.

단점

한국어/마크다운/코드 문서에서 정확도가 떨어질 수 있다. 문장 분리 모델/리소스 관리가 필요하다. 기술 문서의 heading 구조는 따로 처리해야 한다.

dev-ai 적용 평가

문장형 블로그/아티클에는 괜찮다. 하지만 README/docs/코드 섞인 문서에는 heading-aware나 recursive 방식이 더 먼저다.

4-7. spaCy 기반 Chunking

spaCy는 NLP pipeline을 구성할 수 있는 라이브러리다. sentence boundary detection, tokenization, 품사/개체명 인식 같은 pipeline을 연결할 수 있다. sentence boundary detection 자체는 NLP에서 중요한 기본 전처리이며, 도메인과 언어가 복잡할수록 오류가 downstream 품질에 영향을 준다는 연구도 있다. (arXiv)

spaCy 기반 chunking은 보통 이렇게 한다. 1. spaCy로 문장 경계 감지 2. 문장/문단을 chunk_size 기준으로 묶음 3. 필요하면 entity, noun phrase 등 metadata 추가

장점

문장 단위 보존이 좋다. NLP pipeline 확장이 가능하다. 엔티티/키워드 추출과 결합 가능하다.

단점

모델 설치가 필요하다. CPU/메모리 사용량이 character 방식보다 크다. 한국어 모델 품질과 설치 전략을 고민해야 한다.

dev-ai 적용 평가

나중에 Reference 문서에서 keyword/entity 추출까지 하고 싶다면 좋다. 하지만 단순 chunk 개선만 목적이라면 Recursive/Heading-aware가 먼저다.

4-8. Semantic Chunking

Semantic Chunking은 문장이나 문단의 embedding을 보고, 의미가 바뀌는 지점에서 chunk를 나누는 방식이다.

예: 문단 1: Docker 설명 문단 2: Docker Compose 설명 문단 3: PostgreSQL 설명 문단 4: Qdrant 설명 문단 1~2는 의미가 가깝고, 문단 3부터 의미가 바뀌면: Chunk 1: Docker + Docker Compose Chunk 2: PostgreSQL Chunk 3: Qdrant 처럼 나눈다.

SBERT 같은 sentence embedding 모델은 문장을 의미 있는 vector로 만들고 cosine similarity로 비교할 수 있게 해 dense retrieval/semantic similarity에 활용된다. (arXiv)

장점

의미 단위 보존이 좋다. 서로 다른 주제가 한 chunk에 섞이는 문제를 줄일 수 있다. 검색 품질이 좋아질 가능성이 높다.

단점

문장/문단별 embedding 비용이 발생한다. 적재 시간이 느려진다. 구현이 복잡하다. threshold 튜닝이 필요하다. 문서 종류별 편차가 있다.

리소스

CPU: 중간~높음 메모리: embedding batch 크기에 따라 증가 디스크: 결과 chunk 수와 vector 수에 따라 증가 비용: OpenAI embedding 사용 시 비용 증가

dev-ai 적용 평가

고급 개선이다. 지금 당장보다, Reference Pipeline이 어느 정도 안정된 뒤 적용하는 게 좋다.

5. 성능 관점 요약

적재 성능, 즉 ingestion/indexing 속도

빠른 순서: Character → Recursive/Paragraph-aware → Token-aware → Heading-aware → NLTK → spaCy → Semantic → LLM-guided

다만 실제 속도는 구현과 문서량에 따라 달라진다. 가장 느려지는 지점은 보통 이 둘이다.

1. 문장/문단별 embedding을 추가로 수행하는 Semantic Chunking 2. LLM에게 chunk 분리를 맡기는 LLM-guided Chunking

사용 성능, 즉 검색/Ask 시점 성능

검색 시점 성능은 chunking 방식 자체보다 생성된 chunk 수와 Qdrant index 크기에 더 영향을 받는다.

chunk 수가 많다 ↓ vector 수 증가 ↓ 검색 index 커짐 ↓ 디스크/메모리 증가 ↓ 검색 latency 증가 가능

overlap을 크게 하면 chunk 수와 중복량이 증가한다.

chunk_size=800, overlap=100 → step=700 chunk_size=800, overlap=400 → step=400 → chunk 수 크게 증가

즉 overlap은 문맥 보존에는 좋지만, 너무 크면 비용이 늘어난다.

6. 디스크 사용량 관점

디스크 사용량은 대략 이렇게 증가한다.

PostgreSQL: - document_chunks.content 저장량 - overlap으로 인한 중복 content - metadata 컬럼/json 저장량 Qdrant: - vector 수 × vector dimension × float 크기 - payload 저장량

현재 embedding dimension이 1536이라면 vector 하나당 float32 기준 대략:

1536 × 4 bytes = 6144 bytes ≈ 6KB

여기에 Qdrant 내부 index와 payload overhead가 더 붙는다. 즉 chunk 수가 중요하다.

전략 chunk 수 경향 디스크 영향

작은 Character chunk 많음 높음
overlap 큼 많아짐 높음
Paragraph-aware 문서 구조에 따라 보통 중간
Heading-aware 섹션 수에 따라 보통 중간
Semantic threshold에 따라 변동 큼 중간~높음

최종 추천

지금 dev-ai의 다음 개선은 이렇게 가는 게 좋다.

1. CharacterChunker는 유지한다. 2. RecursiveParagraphChunker를 추가한다. 3. chunk_strategy를 DB에 저장한다. 4. heading_path, token_count, metadata_json을 추가한다. 5. Qdrant payload에 metadata를 함께 넣는다. 6. UI에서 chunk 전략과 heading/source/category를 보여준다. 7. 이후 Semantic Chunking은 실험 모드로 추가한다.

면접/포트폴리오 설명은 이렇게 하면 된다.

현재 MVP에서는 전체 RAG 파이프라인을 빠르게 검증하기 위해 character 기반 chunking을 사용했습니다. 다만 character chunking은 문장, 문단, heading, token boundary를 이해하지 못하기 때문에 향후 recursive paragraph-aware, token-aware, heading-aware, metadata-rich chunking으로 개선할 수 있습니다. 특히 dev-ai는 AI Engineering 문서와 URL reference를 다루기 때문에 문서 구조를 보존하는 heading-aware chunking과 source/category/license/heading_path를 함께 저장하는 metadata-rich chunking이 중요합니다. Semantic chunking은 검색 품질 개선 가능성이 있지만, embedding 비용과 구현 복잡도가 커서 후속 실험 단계로 두는 것이 적절합니다.

핵심 결론은 이거다.

지금은 Character Chunking으로 MVP 검증. 다음은 Recursive + Heading-aware + Metadata-rich. Semantic Chunking은 고급 실험 단계.

Indexing / Embedding / Qdrant 이해

Embedding Vector, Qdrant, LLM Provider 구조 설명

현재 dev-ai 시스템의 RAG 구조에서 Embedding Vector, Qdrant, LLM Provider의 역할이 혼동될 수 있으므로, 이를 명확하게 설명합니다.

RAG는 보통 “벡터로 AI에게 직접 조회”하는 구조가 아닙니다.
벡터는 Vector DB에서 관련 문서 chunk를 찾기 위한 검색 표현이고, 최종 AI 모델에는 vector가 아니라 검색된 chunk를 포함한 prompt 텍스트를 전달합니다.

1. 작업 목적 및 주요 오해 방지

다음과 같은 흔한 오해를 방지해야 합니다.

오해 1. Gemma 3, Qwen 2.5, Google Gemini에 vector를 직접 보내서 검색하는 구조다. 오해 2. OpenAI embedding을 쓰면 답변 생성도 OpenAI가 해야 한다. 오해 3. Mock embedding 상태에서도 실제 의미 검색 품질이 검증된다. 오해 4. OpenClaw/Gemma/Qwen/Google Provider가 embedding에도 적용된다.

정확한 설명은 다음과 같습니다:

Embedding Provider는 질문과 chunk를 vector로 변환해 Qdrant 검색에 사용합니다.
LLM Provider는 Qdrant에서 검색된 chunk를 prompt text로 받아 최종 답변을 생성합니다.

따라서 OpenAI embedding + Qdrant + Gemma/Qwen/Google 답변 생성 조합은 완벽하게 가능하고, 이는 일반적인 RAG 구조와도 잘 맞습니다.
2. 현재 코드 기준 사실 정리

현재 시스템은 크게 두 레이어로 나뉩니다: 1. Embedding / Retrieval Layer, 2. LLM Generation Layer

2.1 Embedding / Retrieval Layer

현재 embedding은 app/rag/embeddings.py에서 처리합니다. 지원 모드는 EMBEDDING_MODE=mock과 EMBEDDING_MODE=openai입니다.

[mock] - hashlib 기반 deterministic mock vector 생성 - 실제 의미 검색 품질 검증용이 아님 - 로컬 개발, 파이프라인 테스트용 [openai] - OpenAI embedding API 사용 - model: text-embedding-3-small - dimension: 1536 - 실제 semantic retrieval 품질 검증 가능

현재 OpenClaw, Gemma, Qwen, Google Gemini는 embedding provider가 아니며, 답변 생성 LLM Provider입니다.

2.2 Qdrant Retrieval Layer

Qdrant는 embedding vector를 저장하고 검색하는 역할입니다.

Qdrant point 저장 내용: - id: chunk_id - vector: chunk embedding vector - payload: document_id, chunk_index, title, content, source

Qdrant는 AI 모델이 아닙니다. 질문 vector와 가까운 chunk vector를 찾는 semantic retrieval index입니다.

2.3 LLM Generation Layer

현재 답변 생성 provider는 app/rag/llm_provider.py에서 처리합니다.

FallbackLLMProvider 구조: 1. OpenClawLLMProvider (Gemma 3, Qwen 2.5 등) 2. GoogleLLMProvider (Gemini API) 3. OpenAILLMProvider (OpenAI Chat 모델) 4. MockLLMProvider (테스트 응답)

현재 LLM Provider는 embedding vector를 직접 받지 않습니다. Qdrant에서 검색된 chunk 내용과 prompt template이 결합된 최종 prompt text를 받습니다.

3. 현재 RAG 흐름 설명

현재 시스템의 전체적인 흐름은 다음과 같습니다.

[Indexing Flow] Document ↓ Chunking ↓ Embedding Provider - mock - openai ↓ Embedding Vector ↓ Qdrant Upsert ↓ Vector Index 저장
[Ask Flow] User Question ↓ Embedding Provider ↓ Query Vector ↓ Qdrant Semantic Search ↓ Relevant Chunks ↓ Prompt Builder ↓ LLM Provider - OpenClaw / Gemma / Qwen - Google Gemini - OpenAI - Mock ↓ Answer
Embedding vector는 LLM에게 직접 전달되는 값이 아니라, Qdrant에서 관련 chunk를 찾기 위한 검색 표현입니다.
LLM에게 전달되는 것은 vector가 아니라, 검색된 chunk를 포함한 자연어 prompt입니다.
4. 사용자의 관점 정리

Q. "벡터로 AI에 직접 조회하지 않으니 완전하다고 할 순 없지만, 내부 RAG에서 벡터로 나온 결과를 chunk로 바꾸어서 다시 원래 AI에 검색/질문하는 경우는 흔할 것 같다. 현재 시스템이 어떻게 보면 더 효율적인 것 아닌가?"

이 생각은 대체로 맞습니다. 일반적인 RAG 구조에서는 LLM이 vector를 직접 검색하지 않습니다. Embedding model과 Vector DB가 먼저 관련 chunk를 찾고, 그 결과를 prompt context로 만들어 최종 LLM에게 전달합니다.

따라서 OpenAI embedding으로 검색 품질을 확보하고, 답변 생성은 Gemma, Qwen, Gemini, GPT 등 여러 LLM Provider 중 하나를 사용하는 구조는 충분히 일반적이고 실용적입니다.

이 구조의 장점은 retrieval과 generation을 분리할 수 있다는 점입니다. 검색 품질은 embedding model과 Qdrant가 담당하고, 답변 품질과 문체, 추론 능력은 LLM Provider가 담당합니다.

5. 현재 구조가 효율적인 이유
5.1 Retrieval과 Generation 분리

검색(관련 문서 찾기, top-k chunk 반환)과 생성(검색된 context를 바탕으로 자연어 응답 생성)을 분리하면 여러 LLM을 교체하기 매우 쉽습니다.

예: OpenAI embedding + Qdrant + Gemma 3 OpenAI embedding + Qdrant + Qwen 2.5 OpenAI embedding + Qdrant + Google Gemini Local embedding + Qdrant + Local Qwen
5.2 여러 AI 모델을 같은 RAG 검색 결과에 연결 가능

동일한 질문에 대한 동일한 Qdrant 검색 결과를 여러 LLM에 동시에 전달할 수 있어, 향후 모델 비교나 평가 로그, 피드백 분석에 매우 유리합니다.

5.3 LLM별 context 처리 차이를 비교 가능

같은 chunk를 넣어도 모델마다 답변 품질과 특성이 다릅니다. 이는 모델 교체형 AI 백엔드 포트폴리오로 설명하기 아주 좋은 강점입니다.

  • Gemma: 로컬/온프레미스 실험에 적합
  • Qwen: 코딩/기술 답변에 강점
  • Gemini: API 기반의 안정적 Fallback
  • OpenAI: 품질 비교의 기준점
6. 현재 구조의 한계
6.1 Mock embedding 상태의 한계

Mock embedding은 실제 의미를 이해하지 않습니다. hash 기반 deterministic vector이므로 검색 파이프라인 테스트에는 유용하지만, semantic retrieval 품질 검증에는 부적합합니다.

주의: 현재 Mock Embedding 모드에서는 RAG 파이프라인 동작은 확인할 수 있지만, 실제 의미 검색 품질은 신뢰하기 어렵습니다. 실제 검색 품질 검증에는 OpenAI 또는 Local Embedding Provider를 사용해야 합니다.
6.2 OpenClaw/Gemma/Qwen은 embedding provider가 아님

현재 OpenClaw는 prompt를 받아 답변을 생성하는 LLM Provider이며, embedding vector 생성에는 사용되지 않습니다. (They are generation providers, not embedding providers.)

6.3 Local embedding provider 부재

현재 local LLM 답변 생성은 가능하지만, local embedding provider는 별도로 구현되어 있지 않습니다. 향후 LocalEmbeddingProvider (Ollama embedding, bge-m3, multilingual-e5 등)의 추가가 필요합니다.

7. 결론 / 요약

BomTS Dev AI는 검색을 위해 embedding을 사용하고, 생성을 위해 LLM을 사용하는 전형적이고 실용적인 RAG 아키텍처를 따르고 있습니다.

현재 구조는 맞다. 다만 mock embedding 상태라면 “잘 돌아간다”는 것은 파이프라인 기준이고, “검색 품질까지 좋다”는 뜻은 아니다.

오픈소스 Embedding 고려

향후 로컬 모델 및 확장 계획

현재 BomTS Dev AI는 RAG 파이프라인에서 Embedding Provider와 LLM Provider를 분리하는 구조를 사용합니다. Embedding Provider는 질문과 문서 chunk를 vector로 변환해 Qdrant에서 관련 chunk를 찾는 역할을 하고, LLM Provider는 검색된 chunk를 prompt text로 받아 최종 답변을 생성합니다.

User Question ↓ Embedding Provider ↓ Query Vector ↓ Qdrant Semantic Search ↓ Relevant Chunks ↓ Prompt Builder ↓ LLM Provider - Gemma 3 - Qwen 2.5 - Google Gemini - OpenAI ↓ Answer

중요한 점은 LLM이 vector를 직접 받는 것이 아니라는 점입니다. Vector는 Qdrant에서 관련 chunk를 찾기 위한 검색 표현이고, 최종 LLM에는 검색된 chunk가 포함된 자연어 prompt가 전달됩니다.

Mock Embedding의 의미

Mock embedding은 무작위라기보다는 deterministic fake embedding입니다. 같은 입력에는 항상 같은 vector를 반환하지만, 문장의 의미를 이해하는 모델은 아닙니다. 따라서 문서 등록, chunk 생성, Qdrant upsert, search/ask API 흐름 확인에는 유용하지만, 실제 semantic retrieval 품질 검증에는 적합하지 않습니다.

Mock embedding 상태에서 “시스템이 동작한다”는 것은 파이프라인 연결이 정상이라는 뜻이지, 검색 품질이 좋다는 뜻은 아닙니다.

OpenAI Embedding의 의미

OpenAI embedding은 실제 의미 기반 vector를 생성하므로 Qdrant semantic search 품질을 확인하는 데 적합합니다. 현재 dev-ai는 EMBEDDING_MODE=openai일 때 OpenAI text-embedding-3-small 모델을 사용하는 구조입니다. 다만 OpenAI embedding은 유료 API이므로 API Key, 비용, latency, rate limit, 외부 API 장애, 입력 텍스트가 외부 API로 전달된다는 점을 고려해야 합니다.

Gemma / Qwen / Google과 Embedding의 역할 구분

현재 dev-ai에서 OpenClaw 기반 Gemma 3, Qwen 2.5, Google Gemini는 답변 생성 LLM Provider로 사용됩니다. 이들은 Qdrant 검색용 embedding vector를 생성하는 provider가 아닙니다. RAG 구조에서는 embedding model이 먼저 관련 chunk를 찾고, 그 결과를 prompt text로 만들어 LLM에게 전달합니다.

Search와 Ask

검색과 생성의 차이 및 디버깅 방법
Search와 Ask는 서로 다른 목적을 가진다.

Search는 사용자의 질문을 embedding vector로 변환한 뒤 Qdrant에서 의미적으로 가까운 chunk를 찾는 retrieval 단계입니다.
이 단계에서는 LLM을 호출하지 않습니다.

Ask는 Search 결과를 context로 구성하고, PromptBuilder를 통해 최종 prompt를 만든 뒤 LLM Provider에게 답변 생성을 요청합니다.
즉 Ask는 retrieval과 generation을 결합한 RAG 단계입니다.

디버깅 팁: 답변이 이상할 때는 먼저 Search 결과를 확인해야 합니다.
- Search 결과가 틀렸다면 embedding, chunking, indexing, Qdrant 데이터 문제일 가능성이 높습니다.
- Search 결과가 맞는데 답변이 이상하다면 prompt 구성이나 LLM Provider 문제를 확인해야 합니다.

LangGraph Agent

질문 의도 분류 및 조건부 라우팅 구조

LangGraph Agent는 단순 RAG를 실제 서비스형 AI Workflow로 확장하기 위한 구조입니다.

기본 RAG는 모든 질문을 검색 후 답변 생성 흐름으로 처리합니다. 하지만 실제 AI 서비스에서는 질문 유형에 따라 다른 처리 경로가 필요합니다. 예를 들어 시스템 상태 질문, 사용법 질문, 범위 외 질문, 모호한 질문은 문서 검색 기반 RAG와 다른 방식으로 처리하는 것이 적절합니다.

이 프로젝트는 LangGraph를 사용해 질문 처리 흐름을 여러 단계로 나누어 구성합니다. 먼저 사용자의 질문이 들어오면 classify_intent 단계에서 질문 의도를 분류합니다. 그리고 분류 결과에 따라 rag_answer, system_status_answer, how_to_use_answer, out_of_scope_answer, clarification_answer 중 적절한 처리 단계로 이동합니다. 실제 코드에서도 classify_intent를 시작점으로 두고, intent 값에 따라 각 답변 node로 분기하는 구조를 사용합니다.

이 흐름을 구성하기 위해 LangGraph에서는 State, Node, Edge라는 개념을 사용합니다.

State

State는 질문 처리 과정에서 유지되는 작업 데이터입니다. 단순히 원본 질문만 의미하는 것이 아니라, 질문을 처리하면서 생기는 중간 결과와 실행 정보를 함께 담습니다. 예를 들어 question, intent, answer, sources, provider, model, workflow_steps 같은 값이 State에 담깁니다.

Node

Node는 State를 받아 특정 작업을 수행하는 처리 단계입니다. 예를 들어 classify_intent node는 질문 의도를 판단해 intent 값을 채우고, rag_answer node는 RAG 검색과 답변 생성을 수행하며, out_of_scope_answer node는 범위 밖 질문에 대한 안내 응답을 만듭니다.

Edge

Edge는 Node와 Node 사이의 이동 경로입니다. 일반적인 Edge는 한 단계가 끝난 뒤 다음 단계로 이동하게 하고, 조건이 있는 Edge는 State에 담긴 값에 따라 다음 Node를 선택합니다. 이 프로젝트에서는 classify_intent 단계에서 결정된 intent 값을 기준으로 어떤 답변 node로 이동할지 결정합니다.

이 구조 덕분에 AI Agent의 처리 흐름을 하나의 거대한 함수로 만들지 않고, 질문 분류, RAG 답변, 사용법 안내, 시스템 상태 응답, 범위 외 질문 처리처럼 관찰 가능하고 확장 가능한 단계들의 조합으로 표현할 수 있습니다.

Logs / Feedback / Evaluation

관찰하고 개선할 수 있는 AI 시스템의 핵심
Logs / Feedback / Evaluation은 BomTS Dev AI가 단순한 RAG 데모가 아니라, 관찰하고 개선할 수 있는 AI 시스템이 되기 위한 핵심 구조입니다.

AI 답변은 단순한 함수 결과가 아닙니다. 사용자 질문이 들어온 뒤, 질문 의도 분류, embedding 생성, Qdrant 검색, source chunk 선택, prompt 구성, LLM Provider 호출, 답변 생성, 사용자 피드백까지 여러 단계를 거쳐 만들어집니다.

따라서 최종 답변만 저장해서는 충분하지 않습니다. 질문, 답변, endpoint type, intent, provider, model, latency뿐 아니라, 어떤 source chunk가 검색되었고, 그 score가 얼마였으며, 사용자가 그 답변을 어떻게 평가했는지까지 함께 남겨야 합니다.

  • Ask log는 질문과 답변의 기본 실행 기록입니다.
  • Source log는 RAG 답변이 어떤 문서 chunk를 근거로 생성되었는지 추적하기 위한 기록입니다.
  • Feedback log는 사용자의 평가와 의견을 저장합니다.

이 세 가지가 연결되면 하나의 평가 데이터가 됩니다. 예를 들어 어떤 답변이 down 평가를 받았을 때, 검색된 source가 엉뚱했다면 retrieval 문제이고, source는 적절했지만 답변이 부족했다면 prompt 또는 LLM Provider 문제일 수 있습니다. provider와 model, latency 기록을 함께 보면 어떤 모델이 더 좋은 답변을 만드는지, 어떤 provider가 느리거나 불안정한지도 분석할 수 있습니다.
즉 Logs / Source Logs / Feedback은 RAG 품질 개선을 위한 관찰 데이터이자, 향후 AI가 스스로 답변 품질을 분석하고 개선 방향을 제안하기 위한 평가 데이터셋의 출발점입니다.

상세 기록 및 아키텍처 철학

1. 왜 로그가 필요한가

AI 답변이 만들어지기까지 여러 단계가 관여하므로, 답변이 좋았는지 나빴는지를 판단하려면 최종 답변이 아닌 과정 전체를 남겨야 합니다. 이를 통해 사용자가 문제를 제기했을 때 답변을 재검토하고, 근거를 추적하며, 검색 문제와 생성 문제를 분리하고, 모델과 provider를 비교하며, 궁극적으로 사용자 평가를 단순 감상이 아닌 데이터로 만들 수 있습니다.

2. 현재 dev-ai에서 남기는 로그

ask_logs: 질문, 의도(intent), 답변, provider, model, latency, retrieval_count 등을 담습니다. 누가 무엇을 물었고 어떤 모델이 답했는지 확인합니다.

ask_source_logs: 답변에 사용된 검색 근거(문서 ID, chunk ID, 내용, score, 출처)를 저장합니다. RAG 답변이 이상할 때 가장 먼저 봐야 할 핵심 데이터입니다.

feedback_logs: 사용자의 평가(up/down/neutral)와 의견을 저장합니다. 이 피드백 하나는 단순한 점수가 아니라, 앞서 쌓인 질문, 답변, source, latency 등의 로그 전체와 연결되어 평가 데이터셋을 이룹니다.

3. Source log와 Feedback의 결합이 만드는 가치

RAG 품질은 Retrieval(검색)과 Generation(생성) 두 축으로 결정됩니다. 답변이 이상할 때 Source log가 없다면 이유가 검색 문제인지, 생성 문제인지 구분할 수 없습니다.
사용자가 남긴 "검색 결과는 맞는데 답변이 부족하다"는 Feedback은 Source log와 결합되어, "해당 의도(intent)에서 특정 Provider의 Prompt를 보강해야 한다"는 명확한 개선 지표로 탈바꿈합니다. 즉, AI가 스스로 분석하고 개선 방향을 도출할 수 있는 기반이 됩니다.

4. Latency와 Provider/Model 기록의 중요성

Latency는 단순 성능이 아닌 사용자 경험, 비용, 안정성을 나타내는 지표입니다. 향후 Embedding, 검색, LLM 호출 등 단계별로 Latency를 세분화하면 어떤 구간이 병목인지 파악할 수 있습니다.
또한 OpenClaw 내 여러 모델(Gemma, Qwen 등) 및 Google, OpenAI, Mock 등 다양한 Provider 환경에서 실제로 어떤 모델이 답했는지(혹은 Fallback 되었는지) 기록함으로써 성능 및 비용 효율성을 정확히 비교할 수 있습니다.

5. 향후 발전 방향 (추가 기록 항목 제안)
  • Agent Workflow: 각 Node 통과 내역 및 Intent 분류 이유 명시
  • Embedding & Retrieval 상세: Embedding Provider/Model, Qdrant Collection명, 필터 제외 사유 등
  • Source 상세 토글화: Token 수, Prompt 실제 포함 여부 등을 상세 토글로 관리
  • Prompt & LLM: Prompt Version, Fallback 이유, Token Count 기록
  • Feedback 사유 분류: 사용자가 구체적 사유(잘못된 출처, 짧은 길이, 환각 등)를 체크할 수 있는 UI 도입

AI Engineering Reference Pipeline

개인 AI 지식 실험실로의 발전

AI Engineering Reference Pipeline은 BomTS Dev AI를 개인 AI Engineering Knowledge Lab으로 발전시키기 위한 구조입니다.

수동 문서 등록만으로는 빠르게 변화하는 AI 개발 흐름을 따라가기 어렵습니다.
따라서 이 프로젝트는 AI 기술 블로그, 공식 문서, 모델 릴리스 노트, RAG/Agent/Local LLM 관련 자료를 source registry로 관리하고, URL fetch를 통해 본문을 수집한 뒤, raw reference로 저장합니다.

수집된 reference는 단순 원문 보관에 그치지 않고, 요약, 핵심 변화, 왜 중요한지, dev-ai에 어떻게 적용할 수 있는지, 후속 작업 제안, 주의사항 같은 briefing 정보로 확장될 수 있습니다.
최종적으로 reference는 공통 Document 모델로 변환되고, 기존의 Chunking, Embedding, Qdrant Indexing, Search, Ask 파이프라인을 통해 질의응답에 활용됩니다.

이 구조를 통해 BomTS Dev AI는 단순 RAG 데모가 아니라, AI 개발 트렌드를 수집하고, 해석하고, 내 프로젝트에 적용하기 위한 개인 지식 실험실로 발전할 수 있습니다.
