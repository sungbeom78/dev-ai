# Qdrant 도입 의사결정

## 1. 배경
RAG 시스템에서 텍스트(문서 Chunk)를 검색하기 위해서는 Vector Search 엔진이 필요합니다. 
MVP 환경을 비롯해 향후 상용 수준까지 활용할 수 있는 적절한 Vector DB를 선택해야 했습니다.

## 2. 대안 및 비교
- **Pinecone**: 완전 관리형(SaaS) 서비스로 관리가 편하지만, 로컬/오프라인 환경에서의 테스트가 불가능하고 오픈소스가 아닙니다.
- **Milvus**: 확장성이 매우 뛰어나지만 클러스터 구성이 무겁고 초기 학습 및 설정 비용이 높습니다.
- **pgvector**: 이미 사용 중인 PostgreSQL의 확장이므로 아키텍처가 단순해집니다. 다만, 대용량 트래픽이나 복잡한 필터링에서는 특화된 Vector DB 대비 성능 최적화의 한계가 있을 수 있습니다.
- **Qdrant**: Rust로 작성되어 가볍고 빠르며, Docker를 통한 로컬 배포가 매우 용이합니다. Payload(메타데이터) 필터링이 강력하고 REST/gRPC API를 모두 지원하여 Python 환경과 결합하기 좋습니다.

## 3. 결정
현재 시스템에는 **Qdrant**를 도입하기로 결정했습니다.
1. 개발 환경(Docker) 구성이 매우 직관적이고 가볍습니다.
2. 향후 클라우드 환경(Qdrant Cloud)으로의 전환이 용이합니다.
3. FastAPI/Python 환경에서 `qdrant-client`의 활용성이 높고, 메타데이터 필터링 구조가 본 RAG 구조에 적합합니다.

## 4. 이후 개선 방안
향후 실 트래픽에 맞춰 Indexing 속도나 메모리 사용량이 이슈가 될 경우, HNSW 인덱스 파라미터를 튜닝하거나 pgvector와의 성능 비교 벤치마크를 수행할 예정입니다.
